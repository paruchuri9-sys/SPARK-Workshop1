# SPARK Scenario Design & Quality Framework v1.0

## Core rule
**Authentic facts populate the decision framework; they do not replace it.**

A SPARK scenario is complete only when it creates:
- a consequential judgment,
- meaningful uncertainty,
- diagnostic evidence choices,
- plausible competing interpretations,
- an opportunity to maintain/revise/condition/defer,
- and a reason to reconsider later.

## Standard architecture
1. **Commit** — starting individual judgment, confidence, reasons, key unknown.
2. **Map uncertainty** — what is known, unknown, and how evidence could be acquired.
3. **Prioritize evidence** — limited evidence choice creates value-of-information reasoning.
4. **Interpret evidence** — what it resolves, complicates, or fails to answer.
5. **Decide** — every participant submits; consensus/majority/ties and dissent are preserved.
6. **Perturb** — consequential new information.
7. **Perspective test** — strongest plausible alternative using shared evidence.
8. **Conditions / monitoring** — make decisions implementable and enforceable.
9. **Reconsider** — state what future evidence could reopen judgment.
10. **Reflect / transfer** — identify reasoning opportunities and map them to another context.

## Completeness matrix
Check whether each material dimension is represented or deliberately unresolved:
- decision authority/options
- stakeholder interests
- benefits/opportunities
- costs/risks
- infrastructure/implementation
- economics/resource allocation
- environmental/safety/resilience
- governance/legal/policy
- community/equity/trust
- construction/transition
- expansion/lifecycle
- monitoring/enforcement
- source limits/unknowns
- future evidence/reconsideration

## Evidence packet rules
- Answer at least one important Need-to-Know question.
- Leave at least one consequential uncertainty.
- Use decision-relevant quantities when credible values exist.
- Prefer local/scenario-specific denominators to impressive but irrelevant comparisons.
- Separate primary evidence, later reporting, estimates, and unresolved claims.
- Packets need not be equally useful.
- Avoid purely pro or anti packets unless the record itself truly warrants that.
- Keep each packet readable in roughly 2–4 minutes.
- Never invent a number merely to make the scenario feel complete.

## Scaffold ladder
- **S0** no prompt
- **S1** general process prompt
- **S2** targeted reasoning prompt
- **S3** explicit organizer
- **S4** content-leading / answer-level help (normally avoid during measurement)

Log prompt exposure. Equivalent reasoning with less support is stronger evidence of independence.

## Perturbation rule
A good update should be consequential and preferably resolve one uncertainty while introducing or magnifying another. Decision change is not the objective; defensible maintenance is equally valid.

## Group decision rule
Every participant submits at each formal decision point.
- identical choices = consensus
- different choices = preserve distribution; majority becomes provisional group decision
- tie = unresolved
- preserve strongest dissenting rationale
- convergence is not automatically better

## Low-burden data
Collect:
- choice trajectory
- confidence trajectory
- vote distribution
- evidence choices/order
- Need-to-Know snapshots
- prompt exposure
- time per stage
- response revisions where practical
- perspective-challenge artifact
- reconsideration trigger

Interpret conservatively. Telemetry is evidence about behavior, not direct proof of reasoning quality.

## Pilot protocol
1. Run with 5–8 people.
2. Separate interface confusion from decision uncertainty.
3. Record where facilitators provide content help.
4. Identify packets that answer too much, too little, or the wrong question.
5. Test perturbation balance.
6. Test conditions/reconsideration.
7. Measure timing/workflow friction.
8. Debrief authenticity, reasoning opportunities, scaffolds, observability and transfer.
9. Revise the smallest component that explains the failure.
